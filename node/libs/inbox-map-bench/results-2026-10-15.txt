INBOX MAP STORAGE BENCHMARK - INITIAL COMPARISON BEFORE PRODUCTION SINGLE-KEY SWITCH
Date: 2026-10-15
Host: Apple M3 Pro, 36 GiB RAM, macOS
Base HEAD: d1051d523; current uncommitted Merkle queue implementation.
Build: cargo build --release -p inbox-map-bench --offline
Shared Cargo target configuration was used; target-dir was not supplied.
No production code was changed for these measurements. No commits were made.

Workload:
  One DApp, 1,000,000 inboxes, 10 transitions (base + 10 successors retained).
  Random-looking deterministic full AccountRouting keys; 32-byte account IDs.
  Synthetic Inbox size: 200 bytes, same field shapes as AccountInbox.
  One compacted message-range reference per inbox, no message bodies allocated.
  Hash input: added[32] || consumed[32], like production AccountInbox.
  Actual production QueueMap and OrderedSet source files are compiled by path.
  Legacy storage reconstructs BTreeMap<DApp, Arc<DAppQueue>>,
  BTreeMap<Routing, Arc<Inbox>>, Arc<indexset::BTreeSet> and cursors.
  This measures storage mutation, NOT complete block processing, VM, DB or codec work.
  New inbox allocation and key generation are outside mutation timings.
  Timings include state clone, DApp COW, L2 mutation, and L1 update.
  Each run checks sizes and values of every retained version and the untouched base.
  No benchmark processes were run concurrently.
  Three rounds for 32 changes/block, five rounds for one change/block.
  First-round cold allocation effects are included; summaries report medians.
  step_ms = median individual transition; chain_ms = median sum of 10 transitions.
  retained_delta_mib = live allocator bytes with all successors retained minus
  live bytes before creating the chain; preallocated input inboxes excluded.
  base_live_mib = live allocator bytes used by the initial fixture.
  RSS = whole-process peak from /usr/bin/time -l, includes fixture construction.
  RSS is NOT an incremental-chain measurement and may include freed allocator pages.
  1 MiB = 1,048,576 bytes.

BALANCED LAYOUT: 1000 DAPPS x 1000 ACCOUNTS, RETAINED HISTORY
Benchmark source SHA-256:
  cdc39616eccc660fd01f2626ab0633782fad4609530be5ee0d1303c3307ee35e  src/main.rs
Same host, release build, no production-code changes for this experiment.
Total inbox count remains 1,000,000. DApp 0 uses zero ID; other DApps
use deterministic Blake3 IDs. Account IDs use Blake3(global index).
DApps are populated one at a time; account insertion order is not hash-sorted.
Routing options are explicit: --dapps=1000, default remains --dapps=1.
Each block changes 32 inboxes in 32 distinct DApps.
The original state and 10 consecutive successor versions stay alive together;
no old state is dropped while the chain is built.
Memory checkpoints show extra live allocator bytes for retained successors.
Memory excludes the preallocated update inputs/new inbox values, like earlier runs.
Totals quoted as base + retained delta describe the storage comparison, not full node RSS.
The benchmark still verifies all historical versions against their own expected contents.
A small unit test also checks balanced placement and 11 retained versions against legacy.

Commands:
  cargo run --release -p inbox-map-bench -- merkle update 1000000 32 10 3 --dapps=1000
  Substitute legacy|merkle and update|insert|delete.
  cargo test -p inbox-map-bench --offline
