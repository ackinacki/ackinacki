Comparison:
  indexed = current production Merkle QueueMap + OrderedSet + numeric cursors,
            NOT the earlier std::collections::BTreeMap implementation.
  keyed = raw persistent MultiMap roots, key cursors, cached leaf counts,
          NO OrderedSet and NO array of keys.
  Both layouts reference the same Inbox values and immutable L2 Merkle nodes.
  Rebuilt L1 prototype has exactly the same Merkle root.
  Fixed start positions: one third of the sorted DApps and of each DApp's accounts.
  Synthetic Inbox metadata only, no message payload allocations.

Prototype seek:
  Lower-bound search returning the first key >= cursor, pruning whole subtrees.
  DFS stack holds node references and fixed-size key prefixes.
  Cyclic wrapper does at most one wrap and never emits an inbox twice.
  Tests compare against the native MultiMap iterator for empty maps, deleted
  and missing cursors, boundaries and prefix views at 0,1,4,7,8,129,255,256 bits.

Measurement:
  Five alternating-order rounds, median; warm read-only fixtures.
  WALK = select inboxes only, no common MessagesRange cloning, DB, VM or producer HashMaps.
  WALK sequences are verified with count + order-sensitive checksum for both variants.
  SEEK = initialize both levels and fetch the first inbox at existing keys;
         numeric/key cursor preparation is outside timing.
  ADVANCE = compute new per-DApp cursor keys and global DApp cursor after 32
            accounted consumptions; one DApp * 32 accounts or 32 DApps * 1 account.
            Numeric version does arithmetic only. Key version seeks and walks K%len.
            Persistence/new optimistic-state creation/Merkle updates are EXCLUDED.
  MEMORY = live allocator bytes, NOT RSS. Prototype measured after dropping indexed
           fixture; raw L2 nodes/inbox values remain shared, but all indexes are freed.
  Large indexed DApp counts capped at 10000 to avoid 61+ GiB preallocation.
  This is a feasibility prototype, not a full-block performance measurement.
